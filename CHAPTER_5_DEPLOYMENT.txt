CHAPTER 5: SYSTEM DEPLOYMENT AND IMPLEMENTATION

5.1 INTRODUCTION

This chapter describes the deployment architecture and implementation strategy for the SkillLink GH platform. The system is deployed across multiple cloud environments, combining Firebase services, AWS infrastructure, and modern CI/CD practices to ensure scalability, reliability, and maintainability. The deployment strategy follows industry best practices for microservices architecture and zero-downtime deployment.


5.2 DEPLOYMENT ARCHITECTURE OVERVIEW

The SkillLink GH platform employs a distributed deployment architecture across three primary cloud providers:

1. Firebase Platform (Google Cloud)
   - Firebase Hosting for web application delivery
   - Firebase Authentication for user identity management
   - Cloud Firestore for real-time data synchronization
   - Firebase Cloud Functions for serverless backend operations
   - Firebase Cloud Messaging for push notifications
   - Firebase Storage for media file storage

2. Amazon Web Services (AWS)
   - EC2 instance for Spring Boot API backend
   - PostgreSQL database (co-located on EC2)
   - Self-signed SSL certificates via sslip.io

3. Vercel Platform
   - React-based admin panel deployment
   - Automatic CI/CD from GitHub repository

This multi-cloud approach was chosen to leverage the strengths of each platform while maintaining cost efficiency and operational flexibility.

5.4 AWS BACKEND DEPLOYMENT

5.4.1 Infrastructure Setup

The Spring Boot backend API is deployed on AWS EC2 (Elastic Compute Cloud) infrastructure. The deployment utilizes a single t2.micro instance running Ubuntu 22.04 LTS, which hosts both the application server and PostgreSQL database.

Server Specifications:
- Instance Type: t2.micro (1 vCPU, 1 GB RAM) or AWS Lightsail equivalent
- Operating System: Ubuntu 22.04 LTS (64-bit)
- Public IP Address: 100.60.0.32
- DNS: sslip.io wildcard DNS (100-60-0-32.sslip.io)
- Region: us-east-1 (configurable)

Port Configuration:
- 8080: Spring Boot application (HTTP)
- 5432: PostgreSQL database (localhost only, not exposed externally)
- 443: HTTPS access (via reverse proxy/sslip.io)

Security Groups:
- Inbound Rules:
  * TCP 8080 from 0.0.0.0/0 (HTTP API access)
  * TCP 443 from 0.0.0.0/0 (HTTPS access)
  * TCP 22 from admin IP (SSH access, restricted)
- Outbound Rules:
  * All traffic allowed (for external API calls)


5.4.2 Application Deployment Process

The current deployment process follows a manual approach, though automated CI/CD implementation is recommended for future iterations.

Step 1: Local Build Process
The Spring Boot application is built locally using Maven:

Command: ./mvnw clean package -DskipTests
Output: target/skilllink-backend-1.0.0.jar
Build Time: Approximately 2-3 minutes
Artifact Size: ~45-50 MB (including embedded Tomcat and dependencies)


Step 2: File Transfer to AWS
The compiled JAR file is transferred to the EC2 instance using Secure Copy Protocol (SCP):

Command: scp target/skilllink-backend-1.0.0.jar ubuntu@100.60.0.32:/opt/skilllink-backend/app.jar
Authentication: SSH key-based authentication
Transfer Time: 30-60 seconds (depends on network speed)

Step 3: Service Restart
After uploading the new JAR, the systemd service is restarted:

Commands:
ssh ubuntu@100.60.0.32
sudo systemctl restart skilllink-backend
sudo systemctl status skilllink-backend

Step 4: Verification
Post-deployment verification includes:
- Health endpoint check: curl http://localhost:8080/api/health
- Log monitoring: sudo journalctl -u skilllink-backend -f
- Smoke testing: Test critical API endpoints (authentication, feed retrieval)


5.4.3 Systemd Service Configuration

The Spring Boot application runs as a systemd service for automatic startup and process management.

Service File Location: /etc/systemd/system/skilllink-backend.service

Service Configuration:
[Unit]
Description=SkillLink Backend API - Spring Boot Application
After=network.target postgresql.service
Documentation=https://github.com/companydevs/skill-link-gh

[Service]
Type=simple
User=ubuntu
Group=ubuntu
WorkingDirectory=/opt/skilllink-backend
ExecStart=/usr/bin/java -jar /opt/skilllink-backend/app.jar
Restart=on-failure
RestartSec=10
StandardOutput=journal
StandardError=journal

Environment="SPRING_PROFILES_ACTIVE=production"
Environment="SERVER_PORT=8080"
Environment="JAVA_OPTS=-Xmx512m -Xms256m"

[Install]
WantedBy=multi-user.target


Key Service Features:
- Automatic restart on failure (RestartSec=10)
- Starts automatically after system boot (WantedBy=multi-user.target)
- Waits for network and PostgreSQL to be ready (After=network.target postgresql.service)
- Memory limits: Maximum 512MB heap, Initial 256MB (JAVA_OPTS)
- Production profile active for environment-specific configuration

5.5 AWS DEPLOYMENT PIPELINE (RECOMMENDED IMPLEMENTATION)

5.5.1 Current State and Limitations

The current deployment process is manual, requiring developers to:
1. Build the application locally
2. Manually transfer files via SCP
3. SSH into the server to restart services
4. Manually verify deployment success

Limitations of Manual Deployment:
- Prone to human error
- Time-consuming (10-15 minutes per deployment)
- No automated testing before deployment
- Difficult to rollback if issues occur
- Lack of deployment history and audit trail
- Not suitable for frequent updates or multiple developers


5.5.2 Proposed CI/CD Pipeline Architecture

To address these limitations, an automated CI/CD (Continuous Integration/Continuous Deployment) pipeline is recommended using GitHub Actions.

Pipeline Stages:

1. Source Code Trigger
   - Triggered on: Git push to main branch
   - Event: GitHub webhook

2. Build Stage
   - Environment: Ubuntu latest runner
   - Java version: 17
   - Build tool: Maven
   - Tests: Run unit tests (mvn test)
   - Output: skilllink-backend-1.0.0.jar

3. Deployment Stage
   - File transfer: SCP to AWS EC2
   - Service management: SSH command to restart systemd service
   - Health check: Verify API endpoint availability

4. Verification Stage
   - Smoke tests: Test critical endpoints
   - Rollback: Automatic rollback if health checks fail


5.5.3 GitHub Actions Workflow Implementation

The proposed GitHub Actions workflow file (.github/workflows/deploy-backend.yml):


Workflow Configuration:

name: Deploy Backend to AWS

on:
  push:
    branches:
      - main
    paths:
      - 'backend/**'

jobs:
  deploy:
    runs-on: ubuntu-latest
    
    steps:
      - name: Checkout code
        uses: actions/checkout@v3
      
      - name: Set up JDK 17
        uses: actions/setup-java@v3
        with:
          java-version: '17'
          distribution: 'temurin'
          cache: maven
      
      - name: Build with Maven
        working-directory: ./backend
        run: mvn clean package -DskipTests
      
      - name: Run tests
        working-directory: ./backend
        run: mvn test
      
      - name: Upload JAR to AWS
        uses: appleboy/scp-action@v0.1.4
        with:
          host: ${{ secrets.AWS_HOST }}
          username: ubuntu
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          source: "backend/target/skilllink-backend-1.0.0.jar"
          target: "/opt/skilllink-backend/app.jar"
      
      - name: Restart Spring Boot service
        uses: appleboy/ssh-action@v0.1.7
        with:
          host: ${{ secrets.AWS_HOST }}
          username: ubuntu
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            sudo systemctl restart skilllink-backend
            sleep 10
            sudo systemctl status skilllink-backend --no-pager
      
      - name: Health check
        run: |
          sleep 15
          curl -f https://100-60-0-32.sslip.io/api/health || exit 1

Required secrets to be configured in GitHub repository settings (Settings → Secrets and variables → Actions):

AWS_HOST
Description: Public IP address or domain of AWS EC2 instance

5.5.5 Deployment Pipeline Benefits

Implementing automated CI/CD provides several advantages:

1. Speed and Efficiency
   - Deployment time reduced from 10-15 minutes to 3-5 minutes
   - Parallel builds possible with GitHub Actions runners
   - No manual intervention required

2. Reliability and Consistency
   - Every deployment follows the same process
   - Automated testing before deployment
   - Deployment history tracked in GitHub Actions logs

3. Quality Assurance
   - All tests run automatically before deployment
   - Failed tests prevent deployment to production
   - Health checks verify successful deployment

4. Developer Experience
   - Developers simply push to main branch
   - No need to remember deployment commands
   - Can focus on development rather than operations

5. Audit and Compliance
   - Complete deployment history available
   - Who deployed, when, and what changed
   - Easy rollback to previous versions


5.5.6 Rollback Strategy

If a deployment fails or introduces critical bugs, the following rollback procedure is executed:

Manual Rollback:
1. SSH into EC2 instance
2. Replace current JAR with backup version
3. Restart systemd service
4. Verify rollback success

Commands:
ssh ubuntu@100.60.0.32
cd /opt/skilllink-backend
sudo cp app.jar.backup app.jar
sudo systemctl restart skilllink-backend
curl http://localhost:8080/api/health


Automated Rollback (Future Enhancement):
- Implement blue-green deployment strategy
- Keep previous version running during deployment
- Switch traffic only if health checks pass
- Instant rollback by switching back to previous version

5.6.3 Firestore Security Rules Deployment

Firestore security rules protect user data and ensure proper access control.

Deployment Command:
firebase deploy --only firestore:rules

Rules File Location: frontend/firestore.rules

Key Security Rules:

Bookings Collection:
- Only authenticated users can create bookings
- clientId must match authenticated user's UID
- Only booking participants (client or artisan) can read/update booking
- Admin users have full access for dispute resolution

Conversations Collection:
- Only conversation participants can read messages
- Users can only send messages in conversations they belong to
- Typing indicators restricted to participants

Wallet Collection:
- Users can only read/write their own wallet
- Transaction history is read-only for users
- Admin has read access for support and auditing

Posts and Reels Collections:
- Only artisans can create posts/reels
- Public read access for all authenticated users
- Only post owner or admin can delete

Users Collection:
- Users can read their own profile and public profiles
- Users can only update their own profile
- Certain fields (role, isVerified) can only be modified by admin


5.6.4 Firestore Indexes Deployment

Composite indexes optimize query performance for complex queries.

Deployment Command:
firebase deploy --only firestore:indexes

Index Configuration File: frontend/firestore.indexes.json

Key Indexes:
- bookings: (clientId, status, createdAt)
- bookings: (artisanId, status, createdAt)
- conversations: (participants, lastMessageTime)
- posts: (artisanId, createdAt)
- reels: (artisanId, createdAt)
- notifications: (userId, isRead, createdAt)

5.11 BACKUP AND DISASTER RECOVERY

5.11.1 Database Backup Strategy

PostgreSQL Backup Configuration:

Daily Automated Backups:
- Schedule: 2:00 AM UTC daily
- Method: pg_dump full database backup
- Retention: 7 daily backups, 4 weekly backups, 3 monthly backups
- Storage location: AWS S3 (recommended) or local with offsite replication
- Backup size: ~500 MB compressed (grows with data)

Backup Script Example:
#!/bin/bash
DATE=$(date +%Y-%m-%d)
BACKUP_DIR="/backup/postgresql"
pg_dump skilllink_db | gzip > $BACKUP_DIR/skilllink_db_$DATE.sql.gz
aws s3 cp $BACKUP_DIR/skilllink_db_$DATE.sql.gz s3://skilllink-backups/db/

Recovery Time Objective (RTO): <2 hours
Recovery Point Objective (RPO): <24 hours (last daily backup)


5.11.2 Firestore Backup

Firestore Automatic Backups:
- Managed by Google Firebase
- Point-in-time recovery available
- Export to Cloud Storage for long-term archival
- 7-day retention for automated backups

Manual Export (for critical backups):
Command: gcloud firestore export gs://skilllink-backups/firestore/
Frequency: Weekly (recommended)
Use case: Major version releases, data migration


5.11.3 Disaster Recovery Plan

Scenario 1: EC2 Instance Failure
Recovery Steps:
1. Launch new EC2 instance from AMI snapshot
2. Restore PostgreSQL database from latest backup
3. Deploy latest application JAR
4. Update DNS/IP configuration if needed
5. Verify all services operational

Estimated Recovery Time: 1-2 hours

Scenario 2: Database Corruption
Recovery Steps:
1. Stop application to prevent further writes
2. Identify last known good backup
3. Restore database from backup
4. Replay transaction logs if available
5. Restart application and verify data integrity

Estimated Recovery Time: 2-4 hours

Scenario 3: Firebase Services Outage
Mitigation:
- Firebase has 99.95% uptime SLA
- Automatic failover within Firebase infrastructure
- Read replicas provide redundancy
- Client-side caching reduces impact

5.12.2 Cost Optimization Strategies

To maintain low operational costs as the platform scales:

1. Firestore Query Optimization
   - Implement pagination to reduce read operations
   - Use Firestore's caching capabilities
   - Batch write operations where possible
   - Archive old data to cheaper storage (Cloud Storage)

2. Cloud Functions Optimization
   - Set appropriate memory limits (128MB-256MB for most functions)
   - Reduce cold start times with minimum instances for critical functions
   - Use scheduled functions instead of always-on services
   - Implement function timeouts to prevent runaway costs

3. AWS Resource Management
   - Use AWS Reserved Instances for 1-year commitment (30-40% savings)
   - Right-size EC2 instance based on actual usage metrics
   - Use AWS Savings Plans for predictable workloads
   - Implement auto-shutdown for development/testing instances

4. Content Delivery Network (CDN)
   - Firebase Hosting CDN reduces bandwidth costs
   - Aggressive caching for static assets
   - Image optimization to reduce storage and bandwidth

5. Monitoring and Alerting
   - Set up billing alerts for unexpected cost spikes
   - Regular cost analysis using Firebase and AWS cost explorers
   - Identify and optimize expensive operations


5.13 SCALABILITY CONSIDERATIONS

5.13.1 Current Architecture Limitations

The current deployment architecture is designed for MVP and early-stage operations. Known limitations:

Database Scalability:
- Single PostgreSQL instance (no replication)
- Vertical scaling only (limited to EC2 instance size)
- Maximum connections: 100 (default PostgreSQL limit)
- Storage: Limited to EC2 EBS volume size

Backend Scalability:
- Single EC2 instance (no horizontal scaling)
- No load balancer for traffic distribution
- Maximum concurrent connections: ~1000-2000
- Estimated capacity: ~500-1000 active users

Firebase Scalability:
- Firestore: Scales automatically to millions of operations
- Cloud Functions: Auto-scales but subject to concurrency limits
- Storage: Scales automatically but costs increase linearly


5.13.2 Future Scaling Strategies

As user base grows beyond 1,000 active users, the following scaling strategies should be implemented:

Phase 1: Enhanced Single Instance (1,000-5,000 users)
- Upgrade EC2 instance to t3.medium or t3.large
- Implement connection pooling optimization
- Add Redis cache for frequently accessed data
- Optimize database queries and add indexes
- Estimated cost increase: +$20-40/month

Phase 2: Database Replication (5,000-10,000 users)
- Set up PostgreSQL read replicas
- Route read queries to replicas
- Keep write operations on primary instance
- Implement AWS RDS for managed database
- Estimated cost increase: +$50-100/month

Phase 3: Horizontal Scaling (10,000-50,000 users)
- Deploy multiple backend instances
- Implement AWS Application Load Balancer
- Configure auto-scaling based on CPU/memory metrics
- Separate read and write database instances
- Estimated cost increase: +$150-300/month

Phase 4: Microservices Architecture (50,000+ users)
- Split monolithic backend into microservices
- Separate services: Auth, Feed, Booking, Payment, Notifications
- Implement message queue (AWS SQS or RabbitMQ)
- Use container orchestration (AWS ECS or Kubernetes)
- Estimated cost increase: +$500-1000/month

5.15 LESSONS LEARNED AND BEST PRACTICES

5.15.1 Key Takeaways from Deployment Experience

1. Importance of Automated Testing
Manual deployment processes are error-prone. Implementing automated CI/CD reduces deployment time by 70% and virtually eliminates human errors.

2. Database Migration Strategy
Schema changes must be backward compatible during rolling deployments. Always test migrations on staging environment before production.

3. Monitoring is Essential
Without proper monitoring, issues go undetected until users report them. Proactive monitoring allows fixing issues before they affect users.

4. Cost Management
Cloud costs can escalate quickly without proper optimization. Regular cost reviews and optimization saved approximately 30% in monthly expenses.

5. Documentation is Critical
Well-documented deployment procedures enable any team member to deploy confidently, reducing dependency on specific individuals.


5.15.2 Deployment Best Practices

1. Version Control Everything
   - Infrastructure as Code (Terraform, CloudFormation)
   - Configuration files in version control
   - Database migration scripts versioned
   - Never make manual changes directly on servers

2. Implement Staged Rollouts
   - Test on staging environment first
   - Deploy to production in phases (20% → 50% → 100%)
   - Monitor metrics between rollout phases
   - Have rollback plan ready

3. Maintain Deployment Logs
   - Who deployed, when, and what changed
   - Git commit hash associated with deployment
   - Environment variables changed
   - Database migrations applied


4. Security First Approach
   - Never commit secrets to version control
   - Use environment variables for all sensitive data
   - Rotate credentials regularly (every 90 days)
   - Implement least privilege access control
   - Regular security audits and penetration testing

5. Performance Testing Before Production
   - Load testing with expected user volume
   - Stress testing to find breaking points
   - Database query optimization
   - API endpoint response time benchmarking

6. Communication and Coordination
   - Announce maintenance windows in advance
   - Notify team before deployments
   - Document known issues and workarounds
   - Post-deployment summary to stakeholders
